# The CMS: what she can edit, and how to finish setting it up

Before this, every word on the site was baked into HTML by a build script that
needed the 2 GB crawl archive. She could not change anything without a developer.
That is now fixed for the things she actually edits.

The editor lives at **`/admin`** on her own site.

---

## 1. What she can change herself

| She can | Where in the editor | Pages affected |
|---|---|---|
| Write a **new blog post** | Blog posts and interviews, New | creates a page, appears on `/blog` |
| **Edit or delete** any of the 90 existing posts and interviews | Blog posts and interviews | that page |
| Change a **product name, price, description or badge** | Store products | `/store`, `/products/*`, homepage |
| Change the **homepage numbers** (300+, 200+, 1M+) | Homepage numbers | homepage, About |
| Add, edit or reorder **testimonials** | Testimonials | homepage, product pages |
| Change **homepage headings, intros and the opening paragraph** | Homepage wording | homepage |
| Change the **footer bio and disclaimer** | Homepage wording, Footer | every page |
| Upload an **image** | any image field | wherever she places it |

She writes in a normal rich text editor. She never sees HTML, YAML or git.

## 2. What still needs a developer

Being honest about the edges:

- **Adding a whole new page type** or changing page layout
- **Navigation tabs**, header, footer links, the mobile dock
- The **17 resource libraries** and their 63 child pages, and the **Free Guides**
  sections. These are generated by scripts from her tags, so they update
  themselves when she publishes a post, but the structure is not editable in the UI
- **The contact form** (still has no backend, see `handoff.md`)
- Anything on **Gator**: the store checkout itself, orders, Stripe

## 3. How it works

She edits, the CMS commits to the `homepage-rebuild` branch, the host rebuilds.
There is no database and no server to maintain.

```
/admin  ->  GitHub commit  ->  rebuild  ->  live site
```

The build reads `content/`:

| file | drives |
|---|---|
| `content/blog/*.md` | 90 article pages |
| `content/products.json` | store tiles and product pages |
| `content/stats.json` | the credibility strip |
| `content/testimonials.json` | testimonial cards |
| `content/site.json` | homepage wording and the footer |

Regenerate after an edit with:

```bash
node build-from-content.mjs   # content/ -> rebuild/*.html
node build-static.mjs         # rebuild/ -> dist/
```

**This is the part still to automate.** Right now those two commands run by hand.
On Coolify, point the app at the branch and enable automatic deployment on push,
then add them as a build step so her edit publishes itself. Until that is wired,
her changes land in git but not on the site.

## 4. Setup still to do

### 4a. GitHub access for her

Any git-based CMS needs the editor to have a GitHub account. There is no way
around that short of running a server with its own logins.

1. She creates a free GitHub account.
2. Invite her to `M-Basim78/website` with **Write** access.
3. Send her `https://medpsycmoss.com/admin`.

### 4b. The auth relay

The CMS runs in her browser, and a browser cannot hold a GitHub client secret,
so one small piece of server is required. `docker/cms-auth-worker.js` is that
piece, about 60 lines, free on Cloudflare Workers, stores nothing.

1. GitHub, Settings, Developer settings, OAuth Apps, New OAuth App
   - Homepage `https://medpsycmoss.com`
   - Callback `https://<your-worker>.workers.dev/callback`
2. Cloudflare, Workers, Create, paste the file
3. Add secrets `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET`
4. Put the worker URL into `rebuild/admin/config.yml` as `backend.base_url`
   (currently a placeholder), then rebuild

Until step 4b is done, `/admin` loads and then cannot sign in. It shows a message
saying so rather than a blank screen.

### 4c. Decide how her edits go live

`publish_mode: simple` in the config commits straight to the branch, so her edit
is live as soon as the site rebuilds. Change it to `editorial_workflow` if you
would rather approve her changes as pull requests first. For a solo author who
owns the content, simple is usually right.

## 5. Two things to watch

**Prices must match Gator.** The site advertises the price from
`content/products.json`; Gator takes the actual payment. If she changes one and
not the other, the page and the checkout disagree. The editor says this on the
Store screen, but it is worth saying out loud once. It is also the strongest
argument for eventually moving the store off Gator.

**The disclaimer is a professional requirement.** It is editable, because she may
need to update it, but the field carries a warning. Worth mentioning to her.

## 6. What was actually verified

- 90 articles round-tripped: HTML to markdown and back, and the pages rebuild
  identically from `content/`
- the archive is no longer needed to publish a blog change
- 6 products extracted with their real prices, and a price edit in
  `content/products.json` propagates to the store tiles and product pages
- `/admin` ships in `dist/` and is excluded in `robots.txt`
- 203 pages still build, 0 broken links

Not verified, because it needs the OAuth app to exist: the actual sign-in and a
real commit from the browser. That is step 4b, and it is the last mile.
